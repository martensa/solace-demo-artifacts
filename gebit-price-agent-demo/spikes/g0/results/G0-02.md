## Kurzfassung

- **Variante B1 (Agent-Knoten mit gegatetem Tool) trägt im
  ereignisgetriggerten Lauf.** Anfrage in der Inbox von `marktleitung`
  0,4–2,0 s nach dem Ereignis; Freigabe → Tool ausgeführt 0,39 s;
  Freigabe → Workflow fertig 1,7–2,1 s. Ablehnen, Ablauf, parallele
  Läufe und Antwort per REST funktionieren.
- **Varianten B2/B3 (Gate am Workflow-Tool-Knoten) pausieren nicht.**
  Sie sind fail-closed (Tool wird nie ausgeführt), aber awe öffnet für
  über die Plattform verteilte Workflows keinen HIL-Speicher. Frage an
  Solace.
- **Zwei Risiken für die Messe:** Das `fast`-Modell ruft das gegatete
  Tool gelegentlich doppelt auf (2 von 13 Läufen → zweite Anfrage), und
  ein awe-Neustart hinterlässt verwaiste Anfragen, deren Freigabe das
  Tool ohne lebenden Workflow ausführt.

## Vorbereitung

- Flags `SAM_FEATURE_WORKFLOW_HIL_PAUSE_RESUME` und
  `SAM_FEATURE_WORKFLOW_TOOL_APPROVAL_ENFORCEMENT` (beide `true`);
  `GET /api/v1/config/features`: `resolved: true`, `hasEnvOverride: true`;
  `notify_service` `resolved: true`.
- Feature-Katalog (Binary): Ein gegateter Tool-Knoten pausiert nur mit
  BEIDEN Flags; Enforcement aus → Tool läuft ohne Rückfrage; Enforcement
  wird nach Upgrade von < 2.368 automatisch abgeschaltet, solange alte
  Replikate laufen. Damit ist der Doku-Widerspruch aus D1 erklärt.
- Benutzer `marktleitung` (Keycloak), Rolle `gpos_marktleitung` mit
  `workflow:*:invoke`, `agent:*:invoke`, `notify:_:send`, Claim-Mapping
  und Grant `{type: email}`.

## Befunde

### Rechte und Identität (P2)

- Vor der ersten WebUI-Anmeldung von `marktleitung` wird ein
  Ereignislauf zwar `marktleitung@solace.lab` zugeschrieben, hat aber
  nur die Rechte von `system:default` (`agent:*:invoke`,
  `workflow:*:invoke`): `notify_user` → „access denied …
  notify:_:send“, auch mit Grant per Identität und per `{type: email}`.
- Nach einer einmaligen Anmeldung gelten die Rollen des Benutzers:
  `notify_user` läuft. Doku 2.542.1 (enabling-rbac.md „Where run_as
  Applies“): Event-Mesh-Läufe laufen als echter Benutzer nur, wenn die
  Identität aufgelöst wird. Folge für AKS-Neuaufbau und Preflight:
  jede Laufidentität einmal anmelden.

### Varianten B2/B3: Gate am Tool-Knoten

- `hil` am `tools:`-Eintrag (B3) mit Builtin `get_current_time`:
  Knoten scheitert in 44 ms mit `approvalRefusal: no_approval_route`;
  awe meldet beim Laden „tools require human approval but this workflow
  cannot prompt … configure a session database“.
- awe hat die Session-DB (`session store initialized type=sql`), aber
  `workflow_paused` wird nie angelegt; Strings im Binary: Ohne
  HIL-Speicher startet die Instanz „without it“ (kein Öffnungsfehler) →
  der Speicher ist für Plattform-Workflows nicht verdrahtet; das
  `appConfig` eines Workflows kennt kein `session_service`.
- B2 (Connector-Gate) nicht separat getestet; gleiche Mechanik
  (`approvalRefusal` am Tool-Knoten) [A].

### Variante B1: Agent-Knoten (`gpos-spike-hil-b1`)

Agent `gpos-spike-approver` (`fast`), Gate über `toolsetConfigs`
`hil.get_current_time` (`require_approval: true`). Ereignis →
Workflow → Agent → gegatetes Tool → Notify-Anfrage an
`marktleitung` („Your input is requested“, Kategorie `hil`, A2UI-Karte
„Approval Required“ mit Agent, Tool, `approval_message`, Buttons
Approve/Deny, „Expires in N minutes“).

## Folgen für den Plan

1. **E4/R1:** Nativer HITL = Variante B1. B2/B3 bleiben gesperrt, bis
   Solace die Verdrahtung des Workflow-HIL-Speichers klärt (Frage
   10.1). Monitor-Zähler und Latenzbudget wie für B1 vorgesehen.
2. **Fläche A ist machbar:** Unser Tablet kann über die Notify-API
   antworten, mit einem Token, das `notify:_:send_others` und
   `notify:_:read_others` trägt (hier `sam_admin`). Token-Modell T7/T7b
   bleibt offen; eine Service-Identität mit genau diesen Scopes ist der
   Kandidat.
3. **Doppelaufrufe:** `apply_price` idempotent je `proposal_hash`; der
   BFF beantwortet eine zweite Anfrage zum selben Vorschlag
   automatisch (approve → `already_applied`) und zeigt nur eine Karte;
   Prompt härten; G0-09 misst die Rate über 50 Läufe.
4. **Verwaiste Anfragen (neu, Risiko):** `apply_price` wendet nur an,
   wenn der Vorschlag `pending` ist und die `run_id` zu einem
   lebenden Lauf gehört; der Preflight und jeder awe-Neustart brechen
   offene Anfragen ab (REST `cancelled`, getestet); während der
   Messezeiten kein awe-Neustart. `durable_task_resume` hilft nicht
   (getestet und zurückgenommen).
5. **Identität:** Laufidentitäten nach jedem Neuaufbau einmal anmelden
   (AKS-Runbook, Preflight-Prüfung).
